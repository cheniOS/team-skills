# 团队邮件规范

将中文要点或已有草稿整理为可直接复制的专业英文发送稿，并提供内容对应的中文核对稿。说明用中文，英文使用自然、完整的商务英语；用户明确指定只要某种语言时遵从。不把聊天中的简写口吻带入邮件。

本规范用于统一团队邮件写作，不代表任何公司的官方政策。发布包不保留真实邮件来源及业务记录；通用标题示例与适用边界见 [通用示例与适用边界](references/observations.md)。需要示例或判断适用范围时读取；日常起草无需访问邮箱。

公开写作框架的参考来源、采用范围与调整见 [参考来源](references/sources.md)。仅在询问依据或维护规范时读取；链接不是运行依赖。

## 起草流程

1. 先完成下述角色与目的识别，必要时一次问齐关键缺项，再选模板。
2. 按目的从 [邮件模板](references/templates.md) 选择相关场景，按岗位补充必要证据，删除无关段落，不凑齐栏目。涉及接口协查、请求/响应或日志时，再读 [接口问题与日志脱敏](references/backend-api-issue.md)，采用其中的字段、最小证据和脱敏规则。
3. 按“称呼 → 核心结论/请求及影响 → 必要背景与证据 → 明确行动项 → 致谢 → 签名”组织。首段即可看出写信目的；回复通常只写新增结论和下一步。
4. 信息足够就成稿；姓名、签名等不影响主体的缺项用明确占位符，并在两份正文后的“待补项”列明，不因缺少签名或邮箱阻断起草。不得补造事实、期限、立场或承诺。

## 入口：先识别角色、对象与目的

优先使用当前请求、用户已明确的身份、草稿和线程内容。已有信息不重复询问；历史样本的作者不是当前发件人。“给后端发邮件”只说明收件方，不能据此认定发件人是后端。

- **发件角色/立场**：产品、后端开发、App 开发、测试、QA 或其他；是反馈问题、请求协助，还是代表团队确认/交付？不因所在代码仓库自动选为 iOS 开发。
- **收件对象**：谁需要行动或决策，对方是技术团队、业务方、客户还是管理者？这决定技术细节和表达深度；未知具体邮箱可留待补。
- **邮件目的**：希望对方读完后做什么，例如调查接口、确认规则、审批、提供资料、评审、接收交付，或仅知悉状态。目的优先决定模板，岗位决定事实与证据侧重点。
- **材料与约束**：新邮件/回复、原始要点、附件/日志、期望动作、已确认期限和签名；只追问与本次邮件有关的项。

目的或发件立场不明且会改变正文时，先提出一个合并的简短问题，列出尚缺的角色、目的和收件对象，并请用户补充已有要点/附件情况；不要逐项多轮盘问。用户只调用 Skill、未给内容时，可提供这个简表：

> 发件角色：产品 / 后端 / App / 测试 / QA / 其他  
> 收件对象：姓名或团队（可先不填邮箱）  
> 邮件目的：希望对方做什么  
> 原始要点或材料：背景、附件/日志；有明确期限时一并说明

已经知道任务时，不展示全量入口简表。例如用户只说“写一封产品需求确认邮件”，可以问“请提供收件对象、待确认的具体需求/方案；有附件或明确期限时一并提供”。不要再问已经说明的邮件目的，也不要索要姓名、邮箱、签名等非必要字段作为起草前提；仅在角色会改变确认权限或承诺时追问角色。

材料已清楚表明“请后端调查某接口异常”时直接选问题协查，不再询问邮件目的。角色未知但不影响内容时，用中性立场起草并保留签名待补；涉及批准、验收或代表团队承诺时必须依据用户明确提供的立场。

快速选择 [邮件模板](references/templates.md)：

| 核心目的 | 对应模板 |
| --- | --- |
| 索取资料、资源或协助 | 1 请求 |
| 确认规则/方案、请求审批 | 2 确认；3 澄清 |
| 反馈异常、请求定位或修复 | 4 问题协查；有接口/日志时加专用规范 |
| 征求设计/文档/交付物反馈 | 5 评审 |
| 汇报进展、延期、客服状态 | 6 状态更新 |
| 提供成果、发布或完成通知 | 7 交付 |
| 约会或记录会议决定 | 8 会议 |
| 追踪未完成请求或升级 | 9 跟进 |
| 收到、确认或拉人协作的简短回复 | 10 短回复 |

## 岗位侧重点

统一邮件骨架，按事项选择必要信息，不给所有岗位强塞技术字段。以下为写作侧重点，不规定组织分工；同一人兼任测试和 QA 时按邮件目的选用。

| 岗位 | 正文应优先交代 | 常见附件与正文摘录 |
| --- | --- | --- |
| 产品 | 业务目的、规则、方案差异、边界、待确认决策、验收标准 | 需求文档/流程图：关键规则、变更点、待确认项及章节 |
| 后端开发 | 服务/接口、环境、契约变化、依赖、兼容影响、部署状态、协查请求 | 接口文档/日志：接口与版本、关键字段或错误、脱敏请求/响应及定位 |
| App 开发（iOS/Android） | 平台、版本/build、相关 OS/设备（适用时）、功能表现、交互与接口依赖、交付状态 | 安装包说明/截图/日志：关键变更、复现现象、关联截图或日志位置 |
| 测试 | 测试范围、环境与版本、执行结果、复现步骤、实际/预期结果、缺陷和复测状态 | 测试报告/缺陷清单：结果汇总、关键失败或阻塞项、用例/缺陷 ID |
| QA | 质量状态、验收/发布标准、证据覆盖、未关闭风险、待审批事项 | 质量/验收报告：判定依据、未满足标准、残留风险、需决策项及章节 |
| 设计、项目管理、客服及其他 | 本岗位事项、业务影响、依赖、责任人、下一步 | 对应材料的关键结论、所需动作与定位；无需填写无关技术信息 |

## 标题

新邮件优先：`[Project] Purpose – Specific Topic`。

- Project 为用户本次提供的项目、产品或工作流名称；上下文清楚时可省略。不强行加平台、公司、产品或环境标签。
- Purpose 优先用稳定表达：`Request for`、`Confirmation Required`、`Clarification Required`、`Update on`、`Issue`、`Review Request`、`Delivery`、`Meeting Summary`、`Follow-up`、`Completion`。按语法组合，例如 `Request for [Information]`、`Update on [Task]`、`Confirmation Required – [Topic]`，不要机械重复 Purpose 和 Topic。
- 标题点明具体事项，避免只有 `Question`、`Help`、`Update`。一封邮件围绕一个主要事项。
- 必须区分环境时：`[Project][Environment] Issue – Specific Symptom`。环境取用户原值，`SIT`、`UAT`、`STG`、`PROD` 不视为同一环境。
- 版本、日期、工单号仅在帮助定位时加入；不得编造。只有已确认紧急影响才使用 `Urgent`。
- 回复保留原主题及客户端管理的 `Re:`；转发保留 `Fw:`。不为套规范改旧线程主题，不叠加 `Re: Re:`；新议题另起邮件。
- 用户要求原样保留的标题不改；历史拼写错误不推广到新邮件。

## 跨团队与跨时区沟通

- 首段用一两句交代核心结论、对读者的影响及所需动作。通知类明确是否需要响应；请求类区分“确认收到”“评审反馈”“批准方案”“调查问题”，不要让读者自行猜测。
- 对技术同事提供可复现条件、最小证据和关联 ID；对项目/业务人员先说明范围、交付影响、依赖和所需决策。事实保持一致，仅调整细节深度，不按国籍推断沟通偏好。
- 决策或方案选择类列出有材料支持的备选项、主要收益、代价及约束，并给出基于事实的建议；注明决策范围和待确认人。没有依据时标明尚不能推荐，不编造方案、工作量或偏好。普通单项确认无需强凑多个选项。
- 有期限时使用无歧义日期、时间与当日 UTC 偏移，例如 `[DD Mon YYYY, HH:mm, UTC±HH:mm]`。不要只写 `EOD`、`ASAP`、`tomorrow` 或含糊数字日期。原文不改时在邮件外说明歧义；用户给了相对时间或含夏令时地区且无法确定具体期限时，先核对，不自行换算或假定对方时区。
- 区分“请何时回复/确认”“预计何时修复”“何时发布”与“下一次进展更新时间”。当前不能确认解决时间时，明确尚未确定，并在用户提供了跟进安排时给下一次更新时间；未提供时询问预计时间或跟进安排，不擅自承诺每小时更新或固定响应时长。
- 延期或升级类按照“已知事实 → 实际影响 → 已尝试动作及结果 → 所需支持/决策 → 后续跟进”表达。缺少支持时承认未知；避免暗讽、指责、虚构历史共识及自行扩大抄送名单。
- 使用直接、礼貌的商务英语，少用习语、俚语和复杂委婉表达；缩写首次出现时按读者背景补解释。让收件人能异步作答，不要求立即在线，也不安排未经授权的会议或录制。

## 正文与排版

- 默认 `Dear [Name],`、`Dear [Name A] and [Name B],` 或 `Dear [Team Name] Team,`。熟悉的短回复可沿用 `Hi [Name],`。姓名未知用 `Dear Team,`，不猜称谓、性别或头衔。
- 开头一两句先给核心结论或具体请求，再给必要背景；收到协助的回复可先简短致谢。
- 每段一个意思，段间空行；多项确认用编号，平行信息用项目符号。短邮件两三段即可。
- 长邮件可用 `Background`、`Key Points`、`Action Required` 小标题。多人分工或状态比较可用简单表格；移动端过宽则改列表。
- 行动请求说清“谁、做什么、返回什么”。期限按上文跨时区规则表达；没有时不得自定承诺或期限，可请求预计时间。
- 默认结尾 `Thank you for your support.`，落款 `Best regards,`；避免重复感谢，简单回复可直接落款。
- 使用客户端默认的统一正文字体、字号、颜色；加粗仅突出小标题、决定或关键期限。不复制历史混杂字体、过大空白或第三方免责声明。
- 可复制正文优先用段落、编号、简单列表；仅目标支持时用 Markdown，不用代码围栏包住整封邮件。

## 事实、语气与动作

- 区分观察、推测、结论和请求。错误响应不证明责任方或根因；用 `We observed…`、`Could you please verify…`，避免未经确认的指责。
- `received`、`reviewed`、`confirmed`、`approved`、`resolved`、`deployed`、`verified` 各有含义。收到不等于批准，计划不等于完成，不代替他人确认。
- 请求优先 `Could you please review and confirm…?`、`Please provide…`、`Could you please share the expected completion date?`。催办说明原请求、当前依赖和所需反馈。
- 短回复不强套长模板。确认指出对象与范围；更新给状态和下一步；新增参与人说明原因和动作，不只写 `++loop` 或 `FYI`。
- 保留用户提供的英文、阿文、专有名词、编号和事实；只要求排版时不改措辞。润色指定原文须以用户授权为准。
- 截图、工单、明细作为证据；正文留关键结论，长日志或报告用附件/链接。不强制非技术岗位填写接口、环境和版本。
- 通用示例不带入历史个人联系方式、客户信息、卡号、凭据或会议口令；实际草稿仅使用本次任务必要且已提供的信息。
- 接口 URL、请求/响应、日志、截图和附件都按同一脱敏标准检查；不得仅脱敏正文而保留附件中的原始凭据。保留必要定位信息，具体边界见 [接口问题与日志脱敏](references/backend-api-issue.md)。

## 收件人、附件与签名

- To 放直接行动或决策的人，Cc 放需知情的人。沿用用户提供的对象和线程；不从示例推断固定名单，不默认添加任何联系人。
- 新增参与人说明原因和请求；回复全部、转发和新增收件人按本次用户意图，不自动扩大范围。
- 正文交代附件名称、用途和希望如何处理。未核实文件存在或已添加时，在邮件外标“待附上”，不声称已上传或发送。
- 有报告、说明、需求或证据类附件时，默认在正文给关键结论和必要摘录，让收件人不打开附件也能知道重点、影响与所需动作；不能只写 `Please see the attachment.`。附件承担完整明细。
- 摘要优先列少量关键点（通常 3–5 条，按材料调整），每点尽量包含“结论/问题 → 关键数据或短摘录 → 具体位置”。正文已完整展示时直接加来源定位，不再重复一段摘要。安装包、压缩包等无需硬摘正文，可给版本、内容清单、用途和使用说明。
- 使用实际附件名及已确认版本/日期；定位到页码/章节、工作表/单元格或行、用例/缺陷 ID、截图编号、日志时间或请求 ID。多附件逐项对应，避免只写“见附件第 3 页”却无法判断是哪份。页码有歧义时说明 PDF 页序或文档页码。
- 关键字段、短表格、必要截图或最小日志片段可内嵌，保留单位、环境、范围和预期/实际差异；长表、完整日志及大段原文留附件。脱敏凭据及无关个人信息，不用图片替代可检索的关键编号与结论。
- 摘录必须来自本次已读取的附件或用户给出的明确内容；核对摘要与附件版本一致，保留原文中的条件和限定。未读取、无法解析或缺失附件时，在邮件外标“附件内容待核对”，不编造结论、数据或页码。具体写法见 [附件正文模块](references/templates.md#附件正文模块)。
- 建议附件名：`[Project]_[Topic]_[DocumentType]_[YYYYMMDD].[ext]`，版本仅在用户给出时添加。这是统一建议，非已验证制度。
- 签名顺序：`Best regards,` → 姓名 → 岗位 → 电话（可选）→ 邮箱 → 公司网址（可选）。复用用户自己的已核实签名；未知可省略或占位，不套用他人签名或猜地址。
- 不手写历史引用链、网关警告、手机自动签名或其他公司的法律页脚；客户端已有引用与公司签名由客户端保留。

## 默认输出与检查

默认输出同一封邮件的两份对应文本，按以下顺序分开呈现，方便复制与核对：

1. **英文发送稿**：按需列 `To:`、`Cc:`，再给 `Subject:` 和完整英文正文。
2. **中文核对稿（内部参考）**：给对应中文标题及完整中文正文，段落顺序、编号和行动项与英文一致。回复的实际英文主题保持原样，中文标题只供核对，不替换原线程主题。
3. **待补项**（仅有缺项时）：签名、附件状态、待核对信息和假设，用简短中文列在两份正文之外。

两份稿件使用相同事实、责任人、状态、数字、金额、时间及时区、期限、条件和承诺强度。中文不是删减摘要，不额外补充英文没有的解释或结论。API path、字段名、错误码、版本、ID、实际附件名、日志原文和脱敏代号保持一致，不翻译成另一套技术值；需要说明时在正文之外解释。用户要求原样保留的英文/阿文引文继续保留，中文稿可补对应含义，不能改写原文。

避免中英逐句交错，也不放进整封邮件的双列表格。中文稿用于内部核对；用户另行授权发送时默认仅发送英文稿，只有明确要求双语邮件时才合并发送。只要求检查已有邮件时给检查结果，不强制重写两份；明确指定单语时只输出该语言。用户要求时再给多个备选标题。

未知地址不猜，无需收件人建议时省略 To/Cc；中文稿的姓名、邮箱、电话号码和签名身份与英文相同。

交付前检查：

- 标题是否具体，回复主题是否保留？
- 是否清楚说明现状、所需动作和责任人？多个请求能否逐项回复？
- 首段是否已呈现重点、影响和响应类型？决策邮件是否有足够依据支持选项和建议？
- 日期、时间和当日 UTC 偏移是否无歧义？回复期限、解决时间与下次更新时间是否区分，且没有新增未经确认的承诺？
- 事实、时间、版本、金额、附件状态、责任和承诺是否来自本次材料？
- 有附件时，正文是否展示关键结论与必要摘录，是否标明可检索的文件名和具体位置，是否与实际版本一致？无法核对的部分是否标明？
- 是否把收到/计划/推测写成批准/完成/确认？
- 签名是否属于当前发件人？是否残留无关历史数据或不必要技术细节？
- 必要占位符是否明确告知待补？
