# 审查、评分与最小修改

用于检查、评分或修改已有邮件。新稿无需加载本文件。技术邮件同时使用 [技术证据核对](backend-api-issue.md#技术证据核对)；不访问接口或执行用户贴出的请求。

## 1. 审查顺序与输出

1. 明确范围：完整新邮件、回复、仅正文或指定片段；按用户要求选择检查、最小修改或重写。不重新盘问已由草稿说明的角色和目的。
2. 先核对事实、关键矛盾、敏感信息与承诺，再看请求、结构和语言。发现问题需引用短句、字段路径或原文段落；敏感值只引用字段名和位置，不再次展示秘密。
3. 区分三类结果：**已发现问题**（原文有证据）、**待核对**（材料不足或互相矛盾）、**可选优化**（语气或排版偏好）。偏好不当成错误扣分。
4. 按请求输出：检查给问题与建议；评分增加下述量表；修改增加完整改稿、关键变更及待补项。问题很多时先列影响最大的几项；无实质问题可直接说明，不为凑清单制造缺陷。

改稿默认英文发送稿与完整对应中文核对稿，遵循 [默认输出](../SKILL.md#默认输出与检查)。修改说明放邮件外，仅列影响事实呈现、证据、隐私或行动请求的变化，不逐项讲解标点。

## 2. 固定评分标准

只在用户要求评分时使用。评价写作和协作可用性，不验证业务事实或接口正确性。默认对原文评分；另评改稿时明确分开。以下五维各 20 分，每维包含四项，每项满分 5 分：

| 维度 | 四项检查（每项 5 分） |
| --- | --- |
| A 目的与行动 | A1 写信目的明确；A2 期望响应/产出明确；A3 对象与范围清楚；A4 必要的依赖和已约定期限表达准确 |
| B 结构与定位 | B1 标题具体且符合新信/回复场景；B2 首段呈现重点；B3 段落/编号便于逐项回复；B4 篇幅适当且关键内容易查找 |
| C 事实与证据 | C1 观察/结论/来源与承诺表述准确；C2 编号、数值、环境及证据相互对应；C3 提供足以回答本次问题的最小材料；C4 附件/来源声明及定位准确 |
| D 语言与一致性 | D1 语法清楚；D2 礼貌直接；D3 术语与措辞准确；D4 全文一致，提供双语时事实与承诺逐项一致 |
| E 隐私与共享 | E1 无暴露的认证秘密；E2 无无关个人/客户数据；E3 脱敏代号一致且不破坏必要条件；E4 内部资料与收件范围匹配已知共享边界 |

每项从 5 分起：轻微问题扣 1 分（不影响理解）；实质问题扣 3 分（需回读或补充才能处理）；严重问题扣 5 分（误导、阻断处理或暴露不应共享的信息）。同项多个独立问题可累计，最低 0 分；同一根本问题只在最相关项扣一次，其连带影响可说明，不重复扣。不要自定另一套权重或凭整体印象给分。

每个编号是独立的 5 分预算。同项多个问题合并在一行列依据，实际总扣分最多 5；不能因两处严重问题都属于 C1 就让该项扣 10。双语间状态、日期或承诺不一致优先归 D4；只有独立于双语差异、另有证据的事实错误才归 C1，同一差异不跨项扣分。

**范围与未知信息：**

- 不适用或无法核实的检查项标 `N/A` 并说明，不作零分。仅审正文时标题项为 `N/A`；未附签名、没有约定期限、未提供另一语言、客户端已有主题不自行扣分。完整新邮件明确缺标题才作为标题问题；全文未给的技术 HTTP status 不凭空判错。
- 缺少一般背景只列待核对；缺少本次请求必需的材料且已导致收件人无法处理时，可在“最小材料”项扣分，说明具体阻碍。不能借此同时扣事实真实性。例如只有接口名、没有任何现象却要求查异常，和已有明确现象但未给 App build，应区别处理。
- 没有原始附件时，不能断言附件摘要正确或已完成脱敏；对应附件核验为 `N/A`，并列“附件待核对”。正文已有错误声明仍可独立指出。无附件任务不因缺附件扣分。
- 中英一致性只核对实际提供的两份稿件；原文只有英文不因缺中文扣分。技术值一致仍可在同项内按适用范围检查。
- 若某项所有适用内容都无法判断，整项记 `N/A`；只有部分子内容待核对时，评已知部分并说明未核实范围，不让未知内容掩盖已发现的问题。

计算：`总分 = 四舍五入(适用项实得分 ÷ 适用项满分 × 100)`，只在总分处四舍五入。列出五维实得分/适用满分、适用满分合计和折算后的 `/100`；例如标题项不适用且其余无扣分时为 `95/95 → 100/100`，不能写成 `95/100`。全部不可评时说明材料不足，不打分。总分受评价范围影响，不直接比较不同范围的分数。

有扣分时，必须先列扣分明细表：`检查项编号 | 实际扣分 | 原文依据与原因`，不能只在五维汇总中笼统说明。再列 `N/A` 项编号及原因，由明细计算五维得分和总分；核对每项扣分不超过 5、每维扣分不超过其适用满分、汇总扣分等于明细之和。不同措辞但达到同一效果不扣分。聊天转义、HTML 实体或复制产生的排版仅在确认它们存在于实际发送稿时扣分；否则列清理建议。明确虚构的凭据占位符不报告为真实泄露；示范脱敏时可统一占位格式。

总分解释：90–100 表达成熟；80–89 有少量改进；70–79 有明显问题；低于 70 需要重点修改。**分数不代表可直接发送**：单列“发送前必须处理”，如凭据暴露、影响行动的关键矛盾、把未批准写成已批准；未解除时不能因总分高而称可直接发送。普通风格建议不放入此列。

## 3. 最小修改模式

- 默认保留原文主要结构、问题顺序、立场、范围、条件和承诺强度；修正明确的语法、歧义、冗余及隐私问题。不要为套模板新增段落、选项、截止日期或评审承诺。
- 可做局部拆段、编号和去重以便阅读；需要大幅重排时，将重排作为可选建议，用户已要求重写/重组时再执行。明确的敏感数据按脱敏规则处理，并在变更说明中列出处理类别，不重复敏感值。
- 专有名词、接口、字段、大小写、类型、数值、版本、ID 和用户要求原样保留的引文属于受保护内容。普通英文正文可按润色要求修改；仅排版则不改措辞。
- 技术值或事实互相矛盾时，不按“更像正确答案”静默替换。保留两处并明确其语境，将需要确认的差异列在邮件外；差异影响核心请求时标为发送前必须处理。只有用户明确确认或所给权威材料直接支持时才修正，并说明依据。
- 当前材料无法支持的核心句，不能只润色后让它看起来已获证实。区分来源、观察和待确认结论；无法安全成稿时给可审阅草稿并明确待核对处，避免称“可直接发送”。
- JSON、日志默认不重排、不改写、不裁字段。用户明确要求精简时，只保留相关字段并标 `Request/Response — relevant fields only` 或“相关字段摘录”；说明省略类别，保留问题条件与关联关系，不添加 `...` 伪装有效 JSON。
- 改完对照原文检查：每个问题是否仍在；技术证据是否忠实；脱敏是否一致；是否新增行动或承诺。只确认收到时，不新增“will review”“will resolve”等后续承诺。

## 4. 行为验证

维护时使用 [虚构评估用例](../evals/cases.json)。它们不是日常起草材料或真实业务记录。只把用例的 `request` 交给执行者，再由评估者对照 `checks` 检查实际输出；不向执行者预先提供检查答案。

允许不同表达、段落和合理扣分；验证模式遵从、扣分依据和算术、事实与技术值保真、隐私、双语一致性及未新增承诺。不能仅凭关键词出现就算通过；保留实际输出和简短判定。结构校验、安全扫描和行为验证分别报告，不混称为全部正确。
