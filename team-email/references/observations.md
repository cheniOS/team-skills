# 通用示例与适用边界

以下标题均为虚构的写作示例，不对应真实邮件、公司、客户或项目。`[Project]`、`[Environment]`、`[Version]`、`[Date]` 为占位符，使用时仅填入本次任务已提供的信息。

| 虚构标题示例 | 适用场景与正文重点 |
| --- | --- |
| [Project] Update on Support Case Progress | 客服更新：当前状态、影响、处理顺序、下一步和已确认期限 |
| [Project] Request for Integration Test Accounts | 资料请求：背景、所需资料及格式、用途、反馈时间 |
| [Project] Confirmation Required – Notification Settings | 产品确认：方案、边界、编号确认点、确认后的动作 |
| [Project] Clarification Required – File Upload Requirements | 规则澄清：现有理解、歧义、依据和具体问题 |
| [Project][Environment] API Issue – Search Request Returns an Error | 接口协查：现象、预期/实际、最小脱敏证据、定位信息和所需协助 |
| [Project] Review Request – Account Settings Design | 设计评审：概述、原则、具体条目、截图和待决定事项 |
| [Project] Completion – Acceptance Review for [Version] | 完成通知：经核实成果、适用范围、未关闭项和后续动作 |
| [Project] Delivery – Release Notes for [Version] | 交付通知：内容、位置、验证结果、限制及接收方动作 |
| [Project] Meeting Summary – Planning Review – [Date] | 会议纪要：已确认决定、行动项、责任人、期限和未决问题 |

## 规范性质

标题骨架、目的词表、To/Cc 分工、动作请求、时区、附件命名、签名顺序及交付检查是通用写作建议，不代表任何公司的强制制度。用户提供的岗位流程、公司规范及指定文案优先。

邮件目的决定模板，岗位决定证据侧重点，收件对象决定表达深度。产品、后端开发、App 开发、测试和 QA 可以采用同一结构，但只填写与本次事项相关的事实和证据。不要将测试执行、质量判断、验收批准和发布完成视为同一状态。

有附件时，在正文给关键结论和必要摘录，并标明实际文件名、版本及具体位置；未读取材料时不编造摘要或页码。中英文稿保持内容对应，日志、字段名、文件名和脱敏代号保持一致。

示例不作为人事、采购、法务或财务的专用制度，不构成真实请求、承诺、审批或责任判断。发布包不包含真实邮箱、公司域名、历史邮件主题、实际项目版本、原始日志或业务附件；未来修订示例也应采用占位符或明确虚构内容。
