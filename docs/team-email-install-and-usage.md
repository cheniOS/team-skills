`team-email` 用于起草、修改和检查英文商务邮件，并支持**邮件情绪倾向、原文依据、判断把握、紧迫度和回复建议**分析。已包含 **8 类对外沟通模板、完整英文 Sample、附件模板和写作说明**。

将下面这段发给自己电脑上的 Codex：

```text

https://github.com/cheniOS/team-skills/raw/refs/heads/main/downloads/team-email.zip

请识别当前操作系统和用户主目录，安装到个人技能目录：
~/.agents/skills/team-email/

这里的 ~ 表示我当前操作系统用户的主目录，请你自动换算为本机实际路径。

确保 SKILL.md 直接位于 team-email 目录下，保留 agents、references、assets 和 evals，不要只复制 SKILL.md，也不要形成 team-email/team-email 的重复目录。

如果已安装同名技能，请识别现有安装位置及符号链接，先备份再更新，不重复安装第二份，不覆盖我的业务项目。

安装后检查：
1. Skill 可以被识别。
2. 8 类对外邮件场景和 8 份 CSV 附件模板完整。
```

Codex 通常会自动识别新技能；若未显示，重启 Codex 后再试。[安装目录与识别规则见 OpenAI 官方文档](https://learn.chatgpt.com/docs/build-skills#where-to-save-skills)。

## 二、基本使用方式

在提示词中写上 `$team-email`，再提供项目、联系人、事实、所需动作和时间要求。

- 起草或修改具体邮件时，默认输出 **英文发送稿＋完整中文核对稿**。
- 只要英文时，加一句“只要英文”。
- 只分析邮件情绪时，默认给中文分析和回复建议，不自动生成回复稿。
- 已有草稿可要求“最小修改”；希望调整结构时写“重写或重组”。
- 不确定沟通类型时，直接描述目的，让 Codex 选择合适场景。
- 附件 Sample 是待填写的示例，不是实际业务证据或已经附入邮件的文件。

以下示例任选一条，替换方括号内容即可。没有的信息可注明“未确定”或“不适用”，不要为填满模板编造事实、期限或承诺。

## 三、8 类邮件模板的提示词示例

以下 8 类提示词用于起草具体邮件时，默认同时生成**英文发送稿＋完整中文核对稿**，方便对照。两份稿件的段落、事实、行动项、数字、日期和承诺强度保持对应；中文核对稿仅供内部参考，不自动合并到对外英文正文。明确要求“只要英文”或指定其他单一语言时，才只输出该语言。

### 1. Information Request｜信息或资料请求

```text
使用 $team-email，向合作伙伴索取资料。
项目：[项目名称]
收件人：[联系人]
所需资料：[资料清单、范围和格式]
用途：[下一步工作]
反馈时间：[有明确要求时填写]

请按 Information Request 场景起草。时间未定时询问预计可提供时间，不编造期限。
```

### 2. Clarification｜问题澄清

```text
使用 $team-email，向[联系人]澄清[具体规则]。
项目：[项目名称]
参考资料：[文件、版本和章节]
当前理解：[理解A]
存在的差异：[理解B或冲突示例]

请对方确认适用规则及权威依据，不自行认定哪种解释已经获批。
```

### 3. Progress Update｜进展汇报

```text
使用 $team-email，给[客户联系人]写项目进展邮件。
项目：[项目名称]
已完成：[已核实成果]
进行中：[当前工作]
待解决：[依赖或问题]
下一步：[已确定安排]

本次仅供知情，无需对方行动。不编造完成比例、完成日期或下次更新时间。
```

### 4. Issue Follow-up｜问题跟进与催办

```text
使用 $team-email，跟进合作伙伴的处理进展。
保留原主题：[原邮件主题]
原请求：[日期及具体事项]
最新已确认进展：[已提供的资料或已完成动作]
仍需反馈：[尚待确认的事项]
影响：[已确认的后续依赖]

只跟进未解决部分，不重复索要已提供的内容。完成时间未知时，请对方说明何时能更新调查进展。
```

### 5. Issue Escalation｜重要问题升级

```text
使用 $team-email，向[协调人或决策人]写问题升级邮件。
项目：[项目名称]
已确认问题：[问题及范围]
已采取动作：[实际动作与结果]
实际影响：[受阻工作或里程碑]
需要支持：[具体协调、资源或决定]
尚未确定：[根因、恢复时间等]

语气客观，明确所需支持。不新增收件人，不推断责任、费用或恢复承诺。
```

### 6. Review & Confirmation｜评审与确认

```text
使用 $team-email，请对方评审并确认指定事项。
项目：[项目名称]
文件：[名称、版本及附件状态]
评审人：[联系人]
评审重点：[章节或具体问题]
确认人：[联系人]
需要确认：[规则或范围]
反馈时间：[如有]

分别写清评审意见和确认请求，不把普通确认写成正式批准。
```

### 7. Delivery & Acceptance｜交付与验收

```text
使用 $team-email，准备交付验收邮件。
项目：[项目名称]
接收及验收负责人：[联系人]
交付物：[文件、版本和提供方式]
已完成检查：[实际检查与结果]
验收标准：[已约定标准，未知则注明]
已知限制：[实际未决项]
附件状态：[实际状态]

请对方确认收到，并按标准反馈验收结果。收到不等于验收通过；待附文件在稿外列明，不声称已经附入。
```

### 8. Issue Closure｜问题关闭

```text
使用 $team-email，请求确认关闭问题。
项目：[项目名称]
问题编号：[编号及原始现象]
已验证版本和环境：[版本、环境]
验证范围及结果：[实际记录]
证据：[报告、章节或用例编号]
剩余限制：[如有]
关闭确认人：[联系人]

关闭尚待确认，请写关闭确认请求。若材料只有“已修复或已部署”、没有复测结果，请改为验证请求，不宣布已关闭。
```

## 四、邮件情绪与紧迫度评估

用于判断来信表达出的语气、事项优先级及合适的回应方式。每封邮件分别列出：

| 字段 | 输出内容 |
| --- | --- |
| 情绪倾向 | 满意、积极配合、担忧、催促、不满、语气中性，或信息不足、无法判断；可以是“礼貌但催促”等组合 |
| 原文依据 | 引用支持判断的实际短句，区分最新正文、历史引用和不同发言人 |
| 判断把握 | 高、中或低，并说明理由；极短回复或上下文不足时明确降低把握，不给无依据的精确百分比 |
| 紧迫度 | 高、中、低或待确认；依据期限、阻碍、依赖和最新进展单独判断 |
| 回复建议 | 直接确认、解释情况、回应顾虑、澄清问题或跟进实际负责人，并说明自己是否需要回复 |

判断的是文字表达，不是确定对方的真实心理。催促不等于不满；明确期限也不证明生气。历史抱怨不能归给最新发件人，“已回复”不等于事项完成，只被抄送也不自动意味着需要行动。

### 1. 粘贴邮件正文进行评估

```text
使用 $team-email，分析下面这封来信。

请列出：
1. 情绪倾向。
2. 支持判断的原文短句。
3. 判断把握（高/中/低）及理由。
4. 紧迫度及业务依据。
5. 回复建议，以及我是否需要回复。

区分最新正文和历史引用，不把其他人的措辞归给当前发件人。信息不足时明确说明，不把催促直接判断为不满。
仅分析，不生成回复稿。

邮件：[粘贴正文及必要的往来上下文]
```

### 2. 读取最近 5 封邮件并评估

```text
使用 $team-email，读取我收件箱最近 5 封邮件，结合正文和必要的引用上下文分析。

按收件时间从新到旧列出：
- 主题、发件人及收件时间，并注明时区。
- 情绪倾向。
- 原文依据，注明来自最新正文还是历史引用。
- 判断把握（高/中/低）及理由。
- 紧迫度及业务依据。
- 回复建议、实际行动人，以及我是否需要回复。

同一线程的邮件分别归因，再结合最新进展合并待办，避免重复催办已回答的问题。
信息不足时明确标注，不编造正文、截止时间或完成状态。
仅分析，不生成回复稿，不发送或修改邮件。
```

### 3. 先评估，再根据要点起草回复

```text
使用 $team-email，先分析下面来信的情绪倾向、原文依据、判断把握、紧迫度及回复策略，再根据我的要点起草回复。

来信：[粘贴邮件正文和必要上下文，或指定需要处理的邮件]
我的回复要点：[已确认事实、希望回答的问题及下一步]

提供英文回复稿和完整中文核对稿，保留原主题。
语气适应对方的实际诉求，但不为安抚而编造责任、进度、期限、承诺或批准。
只生成稿件，不自动发送或保存草稿。
```

## 五、只查看模板或修改现有邮件

只想查看完整模板及附件 Sample：

```text
使用 $team-email，给我 Issue Escalation 的完整英文模板和附件 Sample，并说明发送时机、To/CC、准备材料、反馈要求及写作注意事项。
```

修改已有草稿：

```text
使用 $team-email，最小修改以下英文邮件，保留原主题、事实、技术值和承诺强度。给出英文改稿及完整中文核对稿，并列出关键变更。不要发送。
邮件：[粘贴原文]
```

仅检查、不改稿：

```text
使用 $team-email，只检查以下邮件，不改稿。指出事实、措辞、行动请求和附件声明中需要处理的问题，区分已发现问题、待核对项和可选优化。
邮件：[粘贴原文]
```

## 六、发送前核对

生成稿不会自动发送。发送前请核对事实、To/CC、明确日期及时区、实际附件，以及批准、验收或关闭结论是否有依据。
